# Rules.md — Operating Rules for Antigravity on This Project

## 1. Before Writing Any Code
- Read `prd.md`, `technical-requirements.md`, `app-flow.md`, `backend-schema.md`, and `security-access.md` in full before starting any ticket.
- Check `memory.md` first — it reflects the current real state of the project.

## 2. The Non-Negotiable Rule — Tenant Isolation
- **This is a multi-tenant product serving many lodges from one shared backend.** No feature, query, realtime subscription, or storage path may ever allow one lodge to read, write, or infer the existence of another lodge's data.
- Every new table gets a `lodge_id` column and an RLS policy that filters by it **before** any role check.
- Every new query must be scoped by the current user's `lodge_id`, resolved server-side — never trust a `lodge_id` passed from the client.
- Any ticket touching a new table or query is not "done" until tested against at least two seeded lodges confirming isolation.

## 3. Mandatory First Task — Stitch HTML Conversion
- Do not begin any feature ticket until the static HTML generated by Stitch AI has been converted into real Next.js + Tailwind components, per `frontend-specification.md` §4.
- Log completion in `memory.md` before Phase 1 begins.

## 4. Security Non-Negotiables
- RLS policy required before any table is used from the frontend — no exceptions "for now."
- Role checks (admin vs. reception) and tenant checks (lodge_id) enforced at the database level, never only in the UI.
- Never hardcode credentials or the Supabase service role key in frontend/client-exposed code. The service role key is only used server-side (e.g., the registration server function that creates a new `lodges` row).

## 5. Code Style / Minimalism
- Favor simple, direct implementations (align with `ponytail` skill's philosophy). Run `/ponytail-review` or `/ponytail-audit` periodically.
- Don't introduce new dependencies unless clearly justified.

## 6. Data Integrity
- Booking cancellation = status change, never a hard delete.
- Balance due always computed server-side.
- Advance amount must never exceed total amount without explicit override/confirmation.
- A room, booking, or billing row must never reference a `lodge_id` different from the room/booking it's attached to — validate this relationship, don't just assume it.

## 7. Memory Discipline
- **Update `memory.md` after every file created or modified, and after every ticket completed.** Include what was built, decisions made (and why), and what remains open.

## 8. Design Fidelity
- Preserve layout/visual decisions from Stitch and the design-system pass; flag any unilateral redesign.

## 9. Client Requirement Changes
- If a build decision requires assuming an answer to an open PRD question, make the most reasonable assumption, log it clearly in `memory.md`, and flag it — don't block on every open question.

## 10. Testing Before Marking Tickets Done
- Every ticket passes a manual click-through of its flow before being marked complete.
- Every ticket touching data access passes a tenant-isolation check (two seeded lodges, confirm no cross-lodge leakage) before being marked complete — this applies even to seemingly small changes.
